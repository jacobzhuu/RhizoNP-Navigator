# Data Model

Phase 1 introduces the first RhizoNP Navigator domain schema. Phase 2 adds the first literature provenance tables. The goal is to move from generic CSV-RAG records toward explicit scientific entities and traceable paper chunks while preserving the existing retrieval flow.

## Core Tables

- `papers`: literature metadata and provenance.
- `paper_chunks`: structured literature chunks linked to papers.
- `retrieval_runs`: search requests and retrieval parameters.
- `retrieval_results`: ranked chunk-level search results with trace provenance.
- `taxa`: normalized taxonomic entities with rank and external IDs.
- `compounds`: compound entities with structure confidence fields.
- `natural_product_records`: source-specific compound-producer records.
- `datasets`: user or fixture datasets.
- `omics_observations`: individual taxon/metabolite observations with raw labels preserved.
- `omics_associations`: own-data association edges such as 16S-metabolite links.
- `evidence_items`: claim-level evidence records.
- `candidate_links`: evidence-graded candidate relations.

## Design Notes

- UUIDs are generated by the application layer for cross-database testability.
- JSON columns use PostgreSQL JSONB in PostgreSQL and JSON in SQLite tests.
- `metadata` is exposed as `observation_metadata` / `association_metadata` in Python to avoid SQLAlchemy's reserved `metadata` attribute.
- `paper_chunks.metadata` is exposed as `chunk_metadata` in Python for the same reason.
- Retrieval results persist enough provenance to trace each hit from result to chunk to paper DOI/source URL.
- The schema does not claim any external data source is integrated. It only establishes the storage model needed for later ingestion phases.

## Demo Fixture

`data/fixtures/phase1_demo.json` is a synthetic fixture for exercising Phase 1 import and query paths. It is not real literature, not real experimental evidence, and not a natural-product database integration.

Load it into a migrated local database with:

```bash
python -m scripts.load_demo_fixtures
```

## API

The API lives in `rhizonp.api` and exposes a minimal query layer over the migrated domain tables:

- `GET /api/v1/health`
- `GET /api/v1/taxa/{canonical_name}`
- `GET /api/v1/compounds/{canonical_name}`
- `GET /api/v1/taxa/{canonical_name}/evidence`
- `GET /api/v1/taxa/{canonical_name}/candidate-links`
- `GET /api/v1/datasets/{dataset_name}/omics-associations`
- `POST /api/v1/search`

The API depends on `DATABASE_URL` for real database sessions. Tests override the session dependency with in-memory SQLite databases loaded from synthetic fixtures, so the query layer is covered without requiring a running PostgreSQL service.

`POST /api/v1/search` currently uses local BM25 over persisted `paper_chunks`. It records `retrieval_runs` and `retrieval_results`; it does not call external literature APIs or dense embedding models.

## Scientific Boundaries

The schema can represent weak, partial, conflicting, and insufficient evidence states. It does not imply that genus-level taxa produce strain-specific natural products, and it does not turn unknown LC-MS features into confirmed compounds.
